# Environment Specification

The Presolve Environment Specification is the versioned, declarative description of what one execution environment can offer to applications.

Its canonical filename is:

```text
presolve.env.toml
```

The Environment Specification is distinct from both the Application Contract and a Deployment Plan.

```text
Application Contract
    "what the application needs"

Environment Specification
    "what this environment offers and permits"
            │
            ▼
Environment Inventory
    normalized resolver input
            │
            ▼
Resolver
            │
            ▼
Deployment Plan
    "how this application is resolved here"
            │
            ▼
Presolve Node
    concrete provider/runtime materialization
```

## Boundary

An Environment Specification describes environment-facing supply:

- stable environment identity
- allocatable resource capacity
- supported workload execution classes
- stable provider identities and names
- exact capability versions supplied by each provider
- optional semantic capability features actually supported by each provider

It does not describe:

- one particular application deployment
- application-specific capability bindings
- provider credentials
- secrets
- provider SDK configuration
- service endpoints
- infrastructure credentials
- concrete host implementation objects

Those are separate concerns.

Provider implementation configuration belongs at the node/provider realization boundary. Application-specific selection belongs in the Deployment Plan.

## Canonical document

A representative Environment Specification is:

```toml
specification_version = "0.1"

[environment]
id = "env_5c4f14f0-5f7d-4f7a-8df7-b829ef9a0208"
name = "local-dev"
description = "Local Presolve development environment"

[resources]
memory_mib = 4096
cpu_millis = 4000

[execution]
workloads = ["component"]

[[providers]]
id = "prv_e02be85a-84ab-4dd7-b604-b3690357ed90"
name = "memory-services"

[[providers.capabilities]]
interface = "presolve:kv/store"
version = "0.1.0"

[[providers.capabilities]]
interface = "presolve:objects/store"
version = "0.1.0"
features = ["range-read", "user-metadata"]
```

The current schema version is `0.1`.

The currently implemented workload execution class is `component`.

## Identity

Environment and provider IDs are opaque stable identities.

```text
EnvironmentId
    env_<uuid>

ProviderId
    prv_<uuid>
```

They are machine identities, not human-facing names.

Names may change while IDs remain stable:

```text
memory-services  prv_aaa...
        │ rename
        ▼
local-services   prv_aaa...
```

Removing a provider and later creating another provider with the same name represents a new provider instance and therefore receives a new ID:

```text
memory-services  prv_aaa...
        │ delete
        ▼
memory-services  prv_bbb...
```

The same principle applies to environments. Cloning an environment creates a distinct environment identity, and provider instances in that clone should also receive distinct provider identities unless an explicit future feature defines shared identity semantics.

### How IDs are created

IDs are intended to be generated by Presolve tooling when an environment or provider is created.

They are persisted into `presolve.env.toml` so parsing the same document is deterministic and does not create new identities.

The parser does not silently generate missing IDs.

Until the local-development CLI workflow is implemented, manually authored fixtures and Environment Specifications must contain valid IDs explicitly. Chunk 15 is responsible for the user-facing creation and editing workflow around these generated identities.

## Resources

The resource section declares allocatable capacity visible to the resolver:

```toml
[resources]
memory_mib = 4096
cpu_millis = 4000
```

Zero capacity is valid. For example, an environment may be intentionally drained while still remaining a valid environment declaration.

Resource capacity currently represents resolver-visible supply. It is not yet a multi-application scheduler or reservation system.

## Execution support

The execution section explicitly declares workload classes the environment can execute:

```toml
[execution]
workloads = ["component"]
```

Execution support is not inferred from installed providers or node implementation details.

The resolver rejects an application workload when its `WorkloadKind` is absent from this set.

The corresponding resolver problem is:

```text
PS2005 UnsupportedWorkload
```

Additional workload classes such as OCI containers or native executables should be added only when their actual execution model is implemented.

## Providers

A provider is one stable environment-local supply identity:

```toml
[[providers]]
id = "prv_e02be85a-84ab-4dd7-b604-b3690357ed90"
name = "memory-services"
```

One provider may expose multiple capabilities.

For example, the same provider identity may supply both:

```text
presolve:kv/store
presolve:objects/store
```

This is intentional. Provider identity answers "which provider instance was selected?" Capability identity answers "which semantic service is being supplied?"

A provider must expose at least one capability.

Provider IDs and provider names must each be unique within one Environment Specification.

## Capability supply

Provider capabilities use exact semantic versions:

```toml
[[providers.capabilities]]
interface = "presolve:objects/store"
version = "0.1.0"
features = ["range-read", "user-metadata"]
```

The Environment Specification advertises exact versions because it describes concrete supply.

The Application Contract may request a compatible version range, for example:

```toml
[[capabilities]]
interface = "presolve:objects/store"
version = "^0.1"
```

The resolver matches the application requirement against the environment's exact supplied versions.

A provider may supply the same capability interface at multiple exact versions. The same `(interface, exact version)` pair may not be duplicated within one provider.

## Semantic capability enrichment

The raw Environment Specification is converted into a normalized `EnvironmentInventory` before resolution.

```text
Environment Specification
        │
        │ validate + normalize
        ▼
semantic enrichment
        │
        ▼
Environment Inventory
```

For built-in Presolve capability interfaces, enrichment attaches the canonical `CapabilityContract`.

Current built-in semantic contracts include:

```text
presolve:kv/store@0.1.0
presolve:objects/store@0.1.0
```

The enrichment rules are deliberately strict:

```text
known Presolve interface + known exact version
    → attach canonical CapabilityContract

known Presolve interface + unknown version
    → reject

unknown/custom interface + no feature claims
    → preserve as generic capability

unknown/custom interface + semantic feature claims
    → reject
```

A known Presolve capability at a version whose semantics this Presolve release does not understand must not silently degrade into a generic string/version capability.

## Capability features

A canonical capability contract defines the vocabulary of optional semantic features.

A provider advertises only the features it actually supports:

```toml
features = ["range-read", "user-metadata"]
```

The presence of a feature in the canonical contract does not imply that every provider supports it.

During resolution:

- required application features are hard constraints
- preferred application features rank otherwise-compatible providers
- unsupported required features reject the environment
- unsupported preferred features do not reject the environment

The Deployment Plan records only requested features that were actually negotiated.

## Validation and normalization

Environment Specifications reject unknown fields.

Parsing follows this order:

```text
deserialize
→ validate semantic invariants
→ normalize non-semantic ordering
```

Validation intentionally happens before normalization so duplicate declarations cannot be hidden by canonicalization.

Normalization makes these orderings non-semantic:

- workload execution classes
- providers
- provider capabilities
- capability features

Semantically equivalent documents therefore normalize and encode identically.

Encoding also revalidates the specification. Inventory conversion revalidates it as well. This prevents direct Serde deserialization from bypassing semantic invariants.

## Resolution

The resolver consumes the normalized Environment Inventory rather than the authored TOML directly.

Compatibility currently includes:

```text
workload execution support
resource capacity
capability interface
capability version
required semantic features
preferred semantic feature ranking
```

Successful resolution produces a symbolic `DeploymentPlan`.

The plan retains the selected environment ID and provider IDs.

## Materialization

Provider IDs form the stable join from declarative supply to concrete node implementation:

```text
presolve.env.toml
        │
        ▼
EnvironmentInventory
        │
        ▼
Resolver
        │
        ▼
DeploymentPlan
  provider_id = prv_...
        │
        ▼
ProviderRegistry
  prv_... → concrete implementation
        │
        ▼
Runtime
```

The resolver does not hold provider implementation objects.

The node's `ProviderRegistry` associates concrete implementations with the same `ProviderId` values used by the Environment Specification and Deployment Plan.

Materialization fails if the plan selects a provider ID for which the node has no matching concrete implementation.

## Determinism and trust boundary

The Environment Specification is an authored input and must be treated as untrusted until validated.

The implementation rejects, among other invalid cases:

- malformed environment or provider IDs
- unsupported specification versions
- unknown fields
- duplicate provider IDs
- duplicate provider names
- providers with no capabilities
- malformed capability interfaces
- malformed capability versions
- duplicate exact provider capability declarations
- malformed capability feature identifiers
- duplicate capability features
- duplicate workload kinds
- unsupported workload enum values

Normalized serialization is deterministic and idempotent.

## What Chunk 14 establishes

Chunk 14 establishes the environment-side portability contract:

```text
Application Contract
        +
Environment Specification
        │
        ▼
normalized compatibility model
        │
        ▼
deterministic resolution
        │
        ▼
symbolic Deployment Plan
        │
        ▼
provider-ID-based node materialization
```

This proves that application requirements can be resolved against a declarative environment description without placing environment-specific implementation choices into the application release.
