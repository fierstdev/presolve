No behavior changed. Existing text and JSON fixture tests continue to pass.

Reason:

- keep compiler concepts separated
- preserve a clean public API through re-exports
- prepare for parser-backend spike without growing `lib.rs`

## 8. Minimal component graph

Added the first compiler-owned semantic graph above parsing.

`ezc_parser::ParsedFile` now maps into `ezc_core::ComponentGraph`.

The graph currently captures:

- component class name
- custom element name from `@component`
- route path from `@route`
- state fields from `state(...)`
- methods
- render root JSX element
- render JSX attributes
- render bindings

This is the first transition from parser facts to EdgeZero compiler semantics.


## 9. CLI component graph command

Added `ezc_cli graph <file>`.

The command parses TSX through `ezc_parser`, builds an `ezc_core::ComponentGraph`, and prints compiler-owned semantic output.

Added golden fixtures for:

- valid counter component
- broken TSX fixture

This creates the first observable path from source code to parser adapter to compiler semantic graph to user-facing CLI output.


## 10. Component graph semantic diagnostics

Added the first semantic diagnostics to `ComponentGraph`.

New diagnostics:

- `EZC1001`: component class missing `@component(...)`
- `EZC1002`: component class missing `render()`
- `EZC1003`: render binding references an unknown field
- `EZC1004`: event handler references an unknown method

Parser extraction now captures simple event handler references from JSX attributes, such as `this.increment` from `onClick={() => this.increment()}`.

Added semantic-error fixture coverage.


## 11. HTML fixture comparison policy

Adjusted the HTML CLI fixture test to compare normalized HTML instead of raw strings.

Reason:

- editors may format HTML fixtures across multiple lines
- HTML attribute layout whitespace is not the semantic contract for this slice
- the generated element and attributes are the behavior being protected

The empty broken-TSX HTML fixture remains an exact string comparison.


## 12. JSX child preservation

Extended the parser, component graph, and HTML generator to preserve simple JSX children.

Supported child forms:

- normalized JSX text
- JSX expression bindings such as `{this.count}`

Generated HTML now includes static text and binding comments instead of only an empty root element.

This moves the compiler pipeline from structural placeholder output toward real static HTML generation.


## 13. Minimal template graph

Introduced `TemplateGraph` as a distinct compiler graph between `ComponentGraph` and HTML code generation.

Pipeline is now:

- parse TSX
- build component semantics
- build template semantics
- generate static HTML

HTML codegen now consumes `TemplateGraph` instead of `ComponentGraph`.

This separates component-level meaning from DOM/template-level structure and prepares the compiler for richer template analysis.


## 14. CLI template graph command

Added `ezc_cli template <file>`.

The command prints the compiler-owned `TemplateGraph` between component semantics and generated HTML.

This gives the compiler pipeline a visible inspection point:

- `parse`: parser facts
- `graph`: component semantics
- `template`: template semantics
- `html`: generated artifact


## 15. Nested JSX preservation

Extended parser, component graph, template graph, HTML codegen, and CLI template output to preserve nested JSX elements.

`TemplateGraph` now represents a recursive element tree instead of only a flat root with text and binding children.

Added nested JSX fixture coverage for template and HTML output.


## 16. Template binding ownership

Adjusted `TemplateGraph` binding ownership so elements receive binding metadata only for bindings they directly own.

Nested bindings now attach to the nested element rather than being duplicated on ancestors.

This makes generated static HTML closer to a reactive DOM graph where dynamic update points belong to specific template nodes.


## 17. Stable template node IDs

Added deterministic template node IDs to `TemplateGraph`.

Element nodes and binding nodes now receive stable IDs in source-order traversal.

Generated HTML now includes:

- `data-ez-node` on element nodes
- `<!-- ez-binding:<id>:<expression> -->` comments for binding nodes

These IDs create the anchor layer needed for future hydration, resumability, diagnostics, and runtime update hooks.


## 18. Template manifest

Added a machine-readable template manifest generated from `TemplateGraph`.

The manifest records:

- element node IDs and tag names
- binding node IDs and expressions
- event handlers and the element node they attach to

Added `ezc_cli manifest <file>` and JSON fixture coverage.

This creates the first runtime-facing compiler artifact: HTML contains anchors, and the manifest describes what those anchors mean.

## 20. Standalone build page

Updated `ezc_cli build` to write a complete browser-openable `index.html`.

The standalone page includes:

- doctype

- embedded inert JSON template manifest

The `html` command still emits only the fragment. The `build` command now emits a full page plus the separate `template.manifest.json` artifact.


## 21. Tiny browser runtime

Added an emitted `runtime.js` artifact to `ezc_cli build`.

The runtime currently:

- reads the embedded template manifest
- verifies element anchors from `data-ez-node`
- verifies binding anchors from `ez-binding` comments
- sets `data-ez-runtime="ready"` or `"error"` on the document root
- exposes boot state as `window.__EDGEZERO__`
- dispatches an `edgezero:ready` browser event

No state evaluation, event execution, or reactive updates are implemented yet.


## 22. Increment actions in template manifest

Completed Slice 6D-A.

The parser now recognizes the narrow `this.<field>++` expression statement shape inside class methods and records it as a parser-owned state update.

`ComponentGraph` maps those parser facts into compiler-owned action semantics:

- method name
- increment operation
- target state field

The template manifest builder now consumes both `ComponentGraph` and `TemplateGraph` so runtime-facing JSON can include compiler-emitted action records next to template nodes and events.

Current limitation: only increment update expressions are recognized. `this.count += 1` remains unsupported until the later mutation-operations slice.
