## 10. Component graph semantic diagnostics

Added the first semantic diagnostics to `ComponentGraph`.

New diagnostics:

- `EZC1001`: component class missing `@component(...)`
- `EZC1002`: component class missing `render()`

Parser extraction now captures simple event handler references from JSX attributes, such as `this.increment` from `onClick={() => this.increment()}`.

Added semantic-error fixture coverage.

## 12. JSX child preservation

Supported child forms:

This moves the compiler pipeline from structural placeholder output toward real static HTML generation.


## 13. Minimal template graph

Introduced `TemplateGraph` as a distinct compiler graph between `ComponentGraph` and HTML code generation.

Pipeline is now:

- parse TSX
- build component semantics
- build template semantics
- generate static HTML

HTML codegen now consumes `TemplateGraph` instead of `ComponentGraph`.

This separates component-level meaning from DOM/template-level structure and prepares the compiler for richer template analysis.


## 14. CLI template graph command

Added `ezc_cli template <file>`.

The command prints the compiler-owned `TemplateGraph` between component semantics and generated HTML.

This gives the compiler pipeline a visible inspection point:

- `parse`: parser facts
- `graph`: component semantics
- `template`: template semantics
- `html`: generated artifact


## 15. Nested JSX preservation

Extended parser, component graph, template graph, HTML codegen, and CLI template output to preserve nested JSX elements.

`TemplateGraph` now represents a recursive element tree instead of only a flat root with text and binding children.

Added nested JSX fixture coverage for template and HTML output.


## 16. Template binding ownership

Adjusted `TemplateGraph` binding ownership so elements receive binding metadata only for bindings they directly own.

Nested bindings now attach to the nested element rather than being duplicated on ancestors.

This makes generated static HTML closer to a reactive DOM graph where dynamic update points belong to specific template nodes.


## 17. Stable template node IDs

Added deterministic template node IDs to `TemplateGraph`.

Element nodes and binding nodes now receive stable IDs in source-order traversal.

Generated HTML now includes:

- `data-ez-node` on element nodes
- `<!-- ez-binding:<id>:<expression> -->` comments for binding nodes

These IDs create the anchor layer needed for future hydration, resumability, diagnostics, and runtime update hooks.


## 18. Template manifest

The manifest records:

This creates the first runtime-facing compiler artifact: HTML contains anchors, and the manifest describes what those anchors mean.

## 21. Tiny browser runtime

Added an emitted `runtime.js` artifact to `ezc_cli build`.

The runtime currently:

- reads the embedded template manifest
- verifies element anchors from `data-ez-node`
- verifies binding anchors from `ez-binding` comments
- sets `data-ez-runtime="ready"` or `"error"` on the document root
- exposes boot state as `window.__EDGEZERO__`
- dispatches an `edgezero:ready` browser event

No state evaluation, event execution, or reactive updates are implemented yet.


## 22. Increment actions in template manifest

Completed Slice 6D-A.

The parser now recognizes the narrow `this.<field>++` expression statement shape inside class methods and records it as a parser-owned state update.

`ComponentGraph` maps those parser facts into compiler-owned action semantics:

- method name
- increment operation
- target state field

The template manifest builder now consumes both `ComponentGraph` and `TemplateGraph` so runtime-facing JSON can include compiler-emitted action records next to template nodes and events.

Current limitation: only increment update expressions are recognized. `this.count += 1` remains unsupported until the later mutation-operations slice.


## 23. Browser runtime increment actions

Completed Slice 6D-B.

The emitted browser runtime now consumes manifest actions instead of inspecting source code in the browser.

Runtime boot now:

- normalizes handler references such as `this.increment`
- indexes manifest actions by method name
- indexes element anchors from `data-ez-node`
- initializes numeric runtime state from binding initial values
- attaches click listeners for manifest event records
- executes increment actions against the in-memory state object
- updates text nodes immediately following matching binding comment anchors
- keeps component debug state under `window.__EDGEZERO__`

Added an ignored real-browser integration test that builds the nested counter, serves the build output over HTTP, opens it in local headless Chrome, clicks the generated button twice, and verifies `Count:2`, ready runtime status, no missing anchors, and updated debug state.

Current limitation: event handling is still per-node click listeners only. Delegated events are deferred to Slice 6D-D, and the browser test is an explicit ignored test until Slice 6D-E promotes browser coverage into a permanent gate.


## 24. Explicit runtime state store

Completed Slice 6D-C.

The emitted browser runtime now uses an explicit state store instead of direct ad hoc mutation variables.

The store contains:

- component runtime records
- binding callbacks keyed by component and field
- action records keyed by component and method
- element anchors keyed by template node ID

Action execution now flows through `readField`, `writeField`, and `notifyField`. Bindings register update callbacks by field, so a single state write updates every text binding subscribed to that field.

Added a double-binding counter fixture and expanded the ignored real-browser integration test to verify two `{this.count}` bindings update together after two clicks. The browser probe also checks the debug store maps exposed under `window.__EDGEZERO__.store`.

Current limitation: events are still attached directly per element. Delegated event handling remains the next runtime model change.


## 25. Delegated runtime events

Completed Slice 6D-D.

Parser, component graph, template graph, and manifest event semantics now preserve explicit event types. JSX `onClick` becomes compiler-owned event type `click`, and manifest event records now include:

- template node ID
- event type
- handler reference

Template HTML now emits event-specific marker attributes such as `data-ez-on-click`.

The runtime no longer installs per-element click listeners. It builds an event index by event type and template node ID, installs one delegated document listener per event type, walks from the browser event target up through `data-ez-node` ancestors, and dispatches through the manifest action index.

The double-binding browser probe now exercises a nested click target inside one button and a second button wired to a separate handler. Both route through delegated click dispatch and update the subscribed bindings.

Added compiler diagnostics for unsupported event types and duplicate event declarations on the same element.

Current limitation: only delegated `click` is supported; event modifiers and richer propagation semantics are still deferred.


## 26. Browser runtime e2e gate

Completed Slice 6D-E.

The real-browser runtime probe is now a permanent test instead of an ignored manual check. The suite remains implemented as a Rust integration harness so it can reuse the compiler fixture build path without adding a JavaScript e2e dependency.

The browser gate now:

- builds the double-binding counter fixture deterministically
- serves the generated page through an in-test static server
- launches real Chrome through `EDGEZERO_CHROME` or standard local paths
- verifies standalone boot, manifest anchors, initial counter rendering, two increments, nested delegated click dispatch, shared binding updates, and debug store shape
- fails on unexpected `[EdgeZero]` runtime console errors

Added local entry points:

- `pnpm test:e2e`
- `pnpm test:e2e:headed`
- `just e2e`
- `just e2e-headed`

Added `e2e/browser/README.md` to document the permanent gate and `.github/workflows/ci.yml` to run both the Rust workspace tests and the explicit browser e2e job with Chrome installed in CI.

Current limitation: the headed aliases run the same deterministic Chrome dump-DOM harness as the default e2e command. A truly interactive headed runner remains deferred until a DevTools or Playwright-based harness is worth the dependency.


## 27. String state literals

Completed Slice 6E-A.

State initializers now recognize string literals in addition to numeric literals. The parser records the semantic string value rather than the source-quoted spelling, so:

```tsx
name = state("Austin & <Zero>");
```

is carried forward as `Austin & <Zero>`.

The existing template value path now supports string bindings:

- component state fields preserve the unquoted string value
- template binding nodes carry that value as their initial value
- static HTML escapes the rendered text as `Austin &amp; &lt;Zero&gt;`
- manifest JSON serializes the value as a JSON string
- browser runtime initialization uses the manifest value directly instead of coercing every initial value with `Number(...)`

Added `fixtures/0006-string-state` plus parser, core, CLI fixture, and real-browser coverage. The browser e2e suite now boots both the delegated counter fixture and the string-state fixture, verifying `window.__EDGEZERO__` preserves the string state value.

Current limitation: initial values are still represented by the existing `Option<String>` path. The compiler-owned typed serializable value model remains deferred to Slice 6E-D, so numeric initial state is read from the manifest string until a numeric action coerces it during execution.
