Executable evidence

Proofs, not portability slogans.

Each proof isolates an architectural boundary, builds one application release, evaluates it against declared environments, realizes concrete providers, and verifies that application identity did not change.

The useful question is not whether an adapter can be written. It is whether one provider-neutral semantic contract survives materially different implementations while the exact application release remains unchanged.

Common proof shape

The same invariant is tested repeatedly.

01
Build the application release once.

No environment participates in application packaging.

02
Record both identities.

Canonical Presolve release digest + SHA-256 of the exact encoded archive bytes.

03
Evaluate the detached release.

The same archive reconstructs its requirements and is compared with one or more environment definitions.

04
Realize the exact plan-selected provider.

Operational settings and credentials enter only here.

05
Execute the application bytes from the release.

No provider-specific rebuild replaces the detached release.

06
Re-hash and fail on mutation.

Both the logical release digest and raw archive SHA must be unchanged.

What this provider taught us

  • S3 delete-existence must be synthesized with HEAD → DELETE and is not atomic against external mutation.
  • S3-compatible keys have a 1,024-byte provider limit the current capability IR cannot negotiate numerically.
  • The first signed PUT implementation buffers before mutation; multipart/large-object semantics should not be implied by the baseline.

A failure improved the model

The first PostgreSQL conformance attempt exposed a fixture bias hidden by SQLite's dynamic typing: text and bytes had been tested through one column. The fixture was corrected to separate typed text/byte columns. PostgreSQL also forced zero-row column metadata to come from prepared-statement metadata rather than the first returned row.

Presolve does not rewrite SQL. The proof uses a deliberately shared subset and explicit bound parameters; provider-specific dialect dependence remains a negotiated feature.

Identity invariant

Two independent checks prevent a moving target.

Logical releasecanonical manifest → release digest
+
Exact file.presolved bytes → archive SHA-256

A proof fails if either identity changes after planning or execution. This prevents a provider-specific rebuild, regenerated manifest, or silently mutated archive from being presented as portability.

Evaluate critically

The useful question is where the model breaks.

  1. Does an environment-specific assumption leak into the application release?
  2. Are the capability semantics strong enough to make substitution meaningful?
  3. Does the deployment plan expose enough of the decision to audit it?
  4. Can another provider satisfy the contract without changing application code or release identity?
  5. Which provider limits require typed semantic properties rather than boolean feature names?
  6. Which real workload would force Presolve to acknowledge a missing abstraction?
