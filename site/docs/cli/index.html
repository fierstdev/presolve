Docs / CLI + planning

The CLI is designed around different questions. inspect explains semantics, build creates the immutable thing, check answers compatibility, and plan shows the exact symbolic selection before provider materialization.

Developer Preview

Build the current CLI from source.

git clone https://github.com/fierstdev/presolve.git
cd presolve
cargo build -p presolve-cli
export PATH="$PWD/target/debug:$PATH"

presolve --help
Presolve is pre-stable. Public CI packages the CLI for Linux x86_64/arm64 and macOS Intel/Apple Silicon, but tagged binary distribution is still being matured.
Local environment

Start with declared supply.

presolve env init
presolve env provider add memory-services --provides kv,objects
presolve env show
presolve env check

The environment tooling generates/persists stable EnvironmentId and ProviderId values so normal local development does not require hand-managing opaque identities.

The ergonomic --provides shorthand currently covers kv and objects. Advanced/current contracts such as SQL and queues can be declared with exact --capability INTERFACE@VERSION arguments or authored directly in presolve.env.toml.
Four core commands

Four questions, four outputs.

01
presolve inspect — What does this application mean?

Shows the normalized source Application Contract without requiring an environment.

presolve inspect
presolve inspect --json
02
presolve build — What immutable release are we distributing?

Builds/encodes a detached .presolved release whose identity does not include an environment.

presolve build
presolve inspect dist/orders.presolved
03
presolve check — Can this environment satisfy it?

Runs deterministic compatibility and reports structured PS2xxx resolution problems when requirements cannot be satisfied.

presolve check
presolve check dist/orders.presolved --json
04
presolve plan — What exactly did the resolver select?

Emits the symbolic DeploymentPlan: environment identity, workloads, ProviderIds, exact versions, negotiated features, and optional unbound requirements.

presolve plan
presolve plan dist/orders.presolved --json

The exact human output may evolve during preview; the important boundary is that the plan contains semantic/provider identity selection, not database clients, sockets, secrets, or cloud SDK objects.

Automation

Use the versioned JSON projection for tooling.

presolve inspect --json
presolve check --json
presolve plan --json
presolve inspect dist/orders.presolved --json

Every machine payload identifies the explicit CLI schema rather than directly serializing internal Rust structs:

{
  "schema": "presolve.cli",
  "schema_version": "0.1",
  "kind": "..."
}
CommandMachine meaning
inspect --jsonnormalized source application semantics; no environment required
inspect RELEASE --jsonverified immutable release identity and semantics; no environment required
check --jsoncompatibility status + structured resolver problems; no full plan payload
plan --jsonexact symbolic DeploymentPlan when resolved; plan: null when rejected

Rejected check and plan calls write their structured payload to stdout and then return a non-zero status. Automation should branch on stable problem type/code fields rather than scraping human text.

Diagnostics

Stable codes distinguish validation from resolution failures.

RangeSubsystemExamples
PS1xxxApplication ContractPS1001 parse error · PS1005 duplicate capability · PS1016 invalid capability feature
PS2xxxResolutionPS2001 missing capability · PS2004 missing required semantic feature · PS2005 unsupported workload

Application semantic validation can return multiple PS1xxx diagnostics. Resolution failures preserve PS2xxx codes through check, plan, and local execution. Environment Specification validation is typed today but does not yet invent a stable PSxxxx taxonomy merely for symmetry.

{
  "status": "rejected",
  "plan": null,
  "problems": [
    {
      "type": "missing_capability",
      "code": "PS2001",
      "interface": "presolve:kv/store",
      "version": "^0.1"
    }
  ]
}

Local execution

presolve dev closes the loop locally.

The local development path discovers the application/environment, validates compatibility, constructs the plan, materializes local provider/runtime configuration, and executes through the same architecture used by detached-release checkpoints.

presolve env check
presolve check
presolve plan
presolve dev
