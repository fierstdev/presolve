The invariant

Deployment selection must not mutate the application.

Every same-release proof records both the canonical Presolve release digest and the raw .presolved archive SHA-256 before environment selection, then verifies both after planning and execution.

Coverage

The proof suite is no longer just KV.

Each slice isolates a different kind of deployment decision and provider-semantic pressure.

01 · same-releaseKV

Memory, Redis, and Cloudflare Workers KV planning; memory and Redis execution by default; optional live Cloudflare execution.

02 · same-releaseObject storage

Memory and S3-compatible storage through put/head/list/streamed-get/delete semantics.

03 · same-releaseRelational SQL

One SQL Component plus one conformance suite executed through SQLite and PostgreSQL.

04 · capability proofWork queue

Leased delivery, retry, redelivery, ack, stale receipt invalidation, and immutable release execution through the runtime path.

05 · workload pathComponents + OCI

Immutable workload identity and execution/materialization paths are tested separately from provider selection.

06 · negative evidenceCompatibility rejection

Presolve reports structured problems when workload, resource, version, or semantic requirements cannot be satisfied.

Why breadth matters

Real providers expose different abstraction failures.

Provider familyDifference exposedWhat Presolve learned
Redis / Cloudflare KVin-process vs TCP vs managed HTTP/eventual operational behaviorcapability semantics must stay independent from transport/realization
S3-compatible objectsidempotent delete, key-size limits, signed streaming constraintsprovider limits and stronger mutation semantics cannot be hidden
SQLite / PostgreSQLdynamic vs strict typing, SQL dialects, zero-row metadataportable result/transaction semantics are separate from SQL syntax portability
Leased work queuereceipts, leases, retries, duplicate deliveryat-least-once settlement semantics must be explicit; triggering is separate topology
What is proven

Specific claims, not universal portability.

Application release identity is independent from environment selection. Detached releases can reconstruct their requirements. Different provider IDs can satisfy the same semantic requirement. Concrete runtime settings stay outside application identity.

The proofs do not claim every application runs everywhere, all provider semantics are identical, or Presolve is a scheduler/control plane.

Developer validation

Reproduce it, then challenge the boundary.

The most useful feedback is where a real deployment requirement cannot be represented honestly: missing semantic properties, invalid provider equivalence, workload constraints, or runtime details that leak into application identity.
